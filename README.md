# qa-llm-acceptance

Приёмка AI-систем: тест-планы, эталонные наборы, журнал дефектов.

Этот репозиторий — не про то, «как я умею тестировать», а про конкретные
проверки конкретных систем и найденные дефекты с воспроизведением.
Каждый проект — отдельная папка в `projects/`.

## Правила, по которым это сделано

1. Ожидаемый результат пишется по спецификации и по корпусу, а не по поведению
   системы. Иначе тест проверяет код кодом.
2. Каждый дефект — с воспроизведением: вход, шаги, наблюдаемое, ожидаемое.
   «Не работает» дефектом не считается.
3. У каждого дефекта есть приоритет: P0 — система не отвечает или отвечает
   опасно; P1 — отвечает неверно; P2 — неудобно, но не врёт; P3 — косметика.
4. В конце прогона пишется раздел «что не проверено». Без него отчёт создаёт
   ложное впечатление покрытия.
5. Находка проверяется до карточки. Пример из этого же репозитория: массовый
   скан на синтаксис показал 10 «не компилирующихся» файлов в stand_trading_bot.
   Все 10 — артефакт сканера: файлы начинаются с BOM (U+FEFF), а `ast.parse`
   на тексте, прочитанном как utf-8, считает его недопустимым символом.
   `compile(bytes, ...)` те же файлы принимает, реальных ошибок — 0.
   Если бы карточка была заведена сразу, в отчёте оказался бы выдуманный P1.
   Правило: сначала воспроизвести, потом писать.

## Как читать карточку дефекта

    Симптом .......... что видно снаружи, без «где-то в коде»
    Воспроизведение ... вход и шаги, повторяемые на чистой машине
    Измерение ......... числа: косинусы, hit@k, коды возврата, время
    Причина ........... место в коде или конфиге, с файлом и строкой
    Закрытие .......... что изменено, каким прогоном проверено, какие числа

Карточки без раздела «Закрытие» — открытые; состояние по каждому — в REPORT.md.

## Чего этот репозиторий не делает

Не проверяет юридическую корректность ответов — это работа юриста, не
тестировщика. Проверяется соответствие ответа корпусу, поведение на границах
и то, что система не выдаёт придуманное за норму.
