# DEF-010 · P2 · secure-tunnel: описание шифрования расходится с реализацией

Проект: secure-tunnel (ранее tunnel / tunnel-2)
Дата: 2026-10-30
Источник находки: сверка README и кода
Статус: открыт

## Симптом

В коде канал шифруется ChaCha20-Poly1305, ключи согласуются через X25519
и HKDF:

    crypto.py:1   from cryptography.hazmat.primitives.asymmetric import x25519
    crypto.py:5   from cryptography.hazmat.primitives.ciphers.aead import ChaCha20Poly1305

В документации при этом:

    README_SETUP.md:57,90    python generate_key.py
    README.md:17             from cryptography.fernet import Fernet
    (ранняя итерация, README в _older_versions.zip)  «Шифрование AES-256»

То есть: ключи выпускаются в формате Fernet (AES-128-CBC + HMAC), инструкция
по установке описывает Fernet, а трафик шифруется ChaCha20-Poly1305 с X25519.
Три разных утверждения об одном и том же в трёх местах.

## Почему это важно

- Пользователь, следующий README, генерирует ключ «не той» системы и не
  понимает, почему аутентификация не проходит.
- Заявление «AES-256» в описании — фактически неверно для текущего кода.
  Для проекта про безопасность расхождение в описании crypto — это дефект
  первого порядка: доверять остальному описанию уже нельзя.

## Как воспроизвести

    cd secure-tunnel
    grep -n "ChaCha20Poly1305\|x25519" crypto.py        # реализация
    grep -n "Fernet" README.md README_SETUP.md generate_key.py  # документация и ключи

## Предложение

- Один источник правды: описать фактическую схему (X25519 + HKDF +
  ChaCha20-Poly1305) и убрать упоминания AES-256.
- Либо привести генератор ключей к формату, который реально используется,
  либо явно разделить «мастер-ключ доступа» (Fernet) и «ключ канала» (X25519).
- Тест: генерация ключа по инструкции → запуск сервера → успешная
  аутентификация клиента. Сейчас такого сквозного теста нет (0 тестов в проекте).
