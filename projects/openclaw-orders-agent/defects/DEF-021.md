# DEF-021 · P1 · openclaw-orders-agent: автоматизация по входу в систему не работает ни разу

Проект: openclaw-orders-agent
Дата: 2026-11-02
Источник находки: проверка O-10 сокращённого плана (прогон `runs/2026-11-02`)
Статус: открыт

## Симптом

Задача Windows `Orders Agent Summary (logon)` существует и настроена:

    триггер ................. при входе в систему
    действие ................ cmd.exe /c "D:\python projects\openclaw-orders-agent\scripts\daily_summary.cmd"
    последний запуск ........ 09.10.2026 20:39:31
    последний результат ..... 2

В журнале `reports/logon-summary.log` 10 записей, из них:

    ok: true .......... 0
    «API недоступен» .. 9

## Почему это дефект

Автоматизация по входу заявлена в README как то, что решает главную проблему
владельца: компьютер между сессиями выключен, поэтому расписание по часам
срабатывает вхолостую. Но задача вызывает `orders_ops.py summary`, а сводка
требует живого ядра на `127.0.0.1:8800`.

При входе в систему ядро никто не поднимает: задача `OpenClaw Gateway` поднимает
gateway, но не backend AI Freelance Copilot. Значит запасной путь — сам отказ:
он срабатывает всегда и всегда с ошибкой.

Разбор `summary` при погашенном ядре **корректен** (внятное сообщение,
exit 2, файл сводки не затёрт) — дефект не в обработке ошибки, а в том,
что в этом сценарии ошибка гарантирована. Проверка O-09 при этом пройдена:
DEF-011 в части «объяснить причину» исправлен.

## Как воспроизвести

    MSYS2_ARG_CONV_EXCL='*' schtasks /Query /TN "Orders Agent Summary (logon)" /V /FO LIST
    # Результат: 2, последний запуск 09.10.2026

    tail -40 "D:/python projects/openclaw-orders-agent/reports/logon-summary.log"
    # все записи — {"ok": false, "error": "API недоступен ..."}

    # и проверка причины: погасить ядро и вызвать сводку
    python scripts/orders_ops.py summary   # exit 2, «API недоступен»

## Предложение (после уточнения, вариант «поднимать сервис» отозван)

Первый вариант из этой карточки — запускать uvicorn при входе — **неверен** и снят.
Сервис поднимается ради интерактивной работы с копилотом; держать его живым
с момента входа ради ночного отчёта значит жечь память машины ради файла,
который никто не читает в 6 утра.

Ещё важнее: у автоматизации нет источника данных. В ядре MVP единственный
источник заказов — `manual` (`docs/ARCHITECTURE.md`: «Любой источник (сейчас
`manual`, в будущем FL.ru, Kwork, …)»), парсинг площадок сознательно не сделан
(ТЗ §22, README ядра). Заказы появляются только тогда, когда владелец сам
их добавляет и разбирает. Значит сводка «по расписанию» физически не может
сообщить ничего нового: пока машина выключена, новых заказов не возникает,
а когда включена — их приносит человек, а не расписание.

Правильные варианты, по возрастанию объёма:

1. **Сводку не планировать, а вызывать в конце рабочей сессии с копилотом.**
   Ядро уже поднято, заказы уже добавлены — `summary` пишет отчёт по факту,
   без нового сервиса и без расписания. Тогда из README и RUNBOOK убирается
   «запуск по входу в систему», а из задачи Windows — сама задача.
2. **Планировать только тогда, когда есть что суммировать.** Сначала источник
   (`OrderSource` для FL.ru/Kwork — отдельная продуктовая работа, в ТЗ §22
   её нет), потом триггер «после появления новых заказов», а не «при входе».
3. Оставить задачу, но переписать её смысл: не «свежие заказы», а «напоминание,
   что ждёт ручной проверки» — эти данные меняются только действиями человека,
   и сводка нужна тогда же, когда и он.

До выбора варианта формулировку в README и RUNBOOK, что запуск по входу уже
формирует сводку, нужно убрать: сейчас она расходится с фактом 0 из 10.
