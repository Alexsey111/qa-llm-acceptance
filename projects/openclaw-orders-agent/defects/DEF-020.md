# DEF-020 · P1 · openclaw-orders-agent: очередь ручной проверки дублирует заказы

Проект: openclaw-orders-agent
Дата: 2026-11-02
Источник находки: проверка O-06 сокращённого плана (прогон `runs/2026-11-02`)
Статус: исправлено 2026-11-02, проверено повторным прогоном (коммит `b86c68d`)

## Симптом

`orders_ops.py queue` возвращает записи анализа, а не заказы. При повторном
разборе одного и того же заказа в очереди появляется новая строка, а старая
остаётся `pending`.

Замер на прогоне 2026-11-02:

    pending_total: 6
    order 9 — analysis 21 и analysis 16
    order 6 — analysis 18 и analysis 13
    order 2 — analysis 7 и ещё одна
    уникальных заказов: 3, записей: 6

Тот же прогон, `summary`:

    - Заказов ждут решения человека: 3 (записей в очереди: 6)

То есть две команды одного инструмента дают два разных числа на один вопрос.
`summary` дедуплицирует по `order_id` (`cmd_summary`, словарь `queue_orders`),
а `queue` — нет (`cmd_queue`, простой список по `queue["items"]`).

## Почему это дефект

- README обещает «очередь: что ждёт решения человека». Человек видит один
  заказ дважды и не может понять, это два заказа или один.
- Очередь растёт сама: каждый прогон `test` добавляет два `review`-анализа,
  и число записей увеличивается без единого действия владельца (6 → 8 → 10 → 12
  за четыре прогона).
- Расхождение `queue` и `summary` — это ещё и внутреннее противоречие:
  на вопрос «сколько ждёт» инструмент отвечает по-разному в зависимости
  от команды.

## Как воспроизвести

    cd "D:/python projects/openclaw-orders-agent"
    # ядро поднято на 127.0.0.1:8800
    python scripts/orders_ops.py queue
    python scripts/orders_ops.py summary
    # в queue: записей больше, чем уникальных order_id
    # в summary: «Заказов ждут решения человека: 3 (записей в очереди: 6)»

## Предложение

- В `cmd_queue` дедуплицировать по `order_id`, оставляя последний `analysis_id`
  (как это уже сделано в `cmd_summary`), и печатать два числа: заказов и записей.
- В `summary` оставить оба числа, но подписать их явно, чтобы «6 записей на
  3 заказа» не выглядело ошибкой счёта.
- Отдельным решением (уже в ядре, не в агенте): помечать прошлый `pending`-анализ
  при повторном разборе как `superseded`, тогда дублей не будет в источнике.

## Исправление (сделано 2026-11-02)

`scripts/orders_ops.py`, `cmd_queue`: записи группируются по `order_id`,
остаётся самая свежая по `analysis_id`; в выводе теперь два числа —
`pending_total` (заказов) и `pending_records` (записей в источнике).
Имя `pending_total` сохранило прежний смысл «сколько ждёт человека», поэтому
сводка и очередь больше не расходятся.

## Проверка закрытия

    python scripts/orders_ops.py queue
    # pending_total: 3 | pending_records: 14 | уникальных order_id: 3 | повторов: 0

    python scripts/orders_ops.py summary
    # pending_review_orders: 3, pending_review_analyses: 14

Повод проверить ещё раз: 14 записей на 3 заказа — это след от повторных
разборов, а не ошибка вывода. Источник по-прежнему накапливает `pending`
(второй пункт предложения выше), но человек теперь видит заказы.
