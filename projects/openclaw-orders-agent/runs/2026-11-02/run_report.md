## Что это значит

Агент как ручной инструмент сделан аккуратно: контракт соблюдён (решение
не отменяется, черновик отдаётся только при apply, `needs_review` идёт
человеку как есть), ошибки окружения объяснены текстом, а не кодом возврата.

Две дырки — не в разборе заказов, а в том, ради чего проект заявлен:
«снимает рутину по расписанию».

1. **Очередь считается по записям анализа, а не по заказам** (DEF-020).
   Повторный разбор того же заказа добавляет новую запись в очередь, старая
   остаётся `pending`. Владелец открывает `queue` и видит один заказ дважды;
   числа в `queue` и `summary` расходятся (6 против 3). Сам `summary` уже
   дедуплицирует — значит в коде есть два разных ответа на один вопрос.

2. **Автоматизация по входу в систему не работает ни разу** (DEF-021).
   Задача запускает `orders_ops.py summary`, а сводка требует поднятого ядра.
   Ядро при входе никто не поднимает: задача `OpenClaw Gateway` поднимает
   gateway, но не backend на 8800. Результат — 0 успешных из 10 в журнале
   и код возврата 2 у последнего запуска. Запасной путь, который заявлен
   в README как страховка от «компьютер выключен», сам является отказом.

Отдельно, чтобы не выдавать одно за другое: прогон шёл на mock-провайдере.
Он проверяет связку «агент ↔ ядро ↔ API», но не качество ИИ-оценок. Оценки
на реальной модели этим прогоном не проверялись, и в отчёте это записано как
ограничение, а не как «проверено».

## Что не проверено

- Качество ИИ-разбора на реальном провайдере (`is_live=true`): прогон платный,
  отдельная строка бюджета.
- Поведение OpenClaw-агента в дашборде (`orders-operator`): требует запущенного
  gateway и модели в квоте; проверялась только скриптовая часть.
- Ветка «нет сети вообще» (провайдер недоступен, но ядро живо) — не моделировалась.
